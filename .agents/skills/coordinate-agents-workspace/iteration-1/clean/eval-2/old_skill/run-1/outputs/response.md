## "judgment review pending"

That's not a bug — it's one of the Coordinator's completion gates. The skill lists the gate set explicitly: "teammate plan approval, phase reports with approve/reject, completion gates, open decision resolution, and post-mechanical judgment review before synthesis." Judgment review is exactly that last one: a post-mechanical check the run requires before work can be treated as done, separate from your own verification/tests passing.

A couple of things follow directly from how the skill says to handle any rejection:

- Trust the message over any assumption about your provider or setup. Every `coord_*` rejection is "a specific, actionable string, not a generic failure" — so the full rejection text (not just the "judgment review pending" summary) is the actual instruction for what's missing. Don't guess; read it in full.
- Don't bypass it. The teammate workflow is explicit: "If completion is rejected, address the stated gate failure and retry (the same `request_id` is safe — rejections are never replayed from cache); never bypass the gate or claim work that was not performed." So the move is not to retry blindly or find a workaround — it's to satisfy whatever the gate is actually asking for, then call `coord_complete_task` again with the same `request_id`.
- Also worth noting: "Board state — not approval prose inside a rejection — is authoritative." So once whatever judgment-review step needs to happen has happened (this sounds like something the lead resolves, akin to `coord_review_run`/`coord_review_phase` or an open decision via `coord_resolve_decision`), check `coord_status` to confirm the board actually reflects it rather than trusting your own read of the rejection text alone.

Practically: read the full rejection, figure out what it's waiting on (most likely a lead-side review step hasn't happened yet for this run/phase), and if it's not something you as a teammate can resolve yourself, that's exactly the kind of thing to flag to the lead via `coord_send_message` rather than sit on — silence past a claimed task reads as stalled, and a completion you can't get past a gate is a blocker worth surfacing, not a puzzle to route around.

## Copilot never getting a task handle from coord_wait

This is expected, not a bug, and there's nothing to work around. Straight from the Provider compatibility section: "The MCP Tasks extension (`coord_wait`/`coord_await_run` durable handles) only activates when your MCP client declares `io.modelcontextprotocol/tasks`; clients that don't simply get the blocking result instead — this is a capability check, not a provider allowlist, so don't infer anything about provider support from whether you receive a task handle."

In other words, whether you get a durable task handle back depends on whether the *MCP client* (the CLI's own MCP implementation) declares that Tasks capability on its requests — it has nothing to do with which provider (Claude vs. Copilot) is driving the session. Your Claude client evidently declares it; the Copilot teammate's client apparently doesn't, so it just gets the normal blocking result from `coord_wait` instead of a pollable handle. Functionally the teammate still gets the same eventual result — same tool result a blocking client would have received — just without the ability to `tasks/get`-poll it separately.

So: not something to patch around in your workflow. The only case the skill tells you to flag is if a client behaves *unexpectedly* — "schema rejected, structured content ignored, elicitation not surfaced" — where another provider handles the identical call fine; that's called out as "a client-side MCP implementation gap in that CLI, not a Coordinator-side special case to work around," and the instruction there is to `coord_publish_finding` it so the lead and other lanes know. But the plain absence of a task handle for a client that doesn't declare the Tasks capability isn't that case — it's documented, capability-gated behavior, so no finding needed and no fix required on your end.
